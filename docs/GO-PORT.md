# Go port

The backend moves from TypeScript (TanStack Start on Nitro, Node 24, `apps/app/src/server`) to one Go binary. The React dashboard stays and becomes a static single-page app that the binary serves. The model for this work is the Palui port: read `~/selfhost/palui/docs/GO-PORT.md` first (rules, Compatibility contracts, Decisions log, Cutover). That repo is a read-only reference, and its Go packages under `~/selfhost/palui/apps/server/internal` may be copied where they fit.

This file is the working plan. The agent doing the work loses its memory when its context is compacted, and review agents start with none, so everything a later step needs is written here. Update the Status table, the Decisions log and Known gaps as you go, before you move to the next milestone.

## Why, and what to expect

Measured in production on 2026-11-14 (Mac mini, container `recall-app-1`, image `recall:latest`):

- Image 332 MB: Debian base 97 MB, Node 145 MB (the `node` binary is 123 MB), app output 82 MB (sharp and libvips 37 MB, `libonnxruntime.so` 25 MB).
- Memory: the main Node process holds about 90 MiB. The embedding child (`embed-child.mjs`) holds 290 MiB idle-loaded and 460 to 571 MiB right after loading. It is killed after 600 s idle. The container peaked at 1083 MiB in 9 hours.
- Data volume: `recall.db` 32 MB, model files 130 MB under `/data/models`.

Most of the memory is the e5 model and ONNX Runtime, which Go keeps. The honest target is an image near 90 MB, about 25 MiB with the model unloaded, and 200 to 350 MiB with it loaded. These are estimates. M0 measures them.

## Rules

1. The TypeScript source is the spec. Port behavior exactly: status codes, error codes and texts, limits, timeouts, backoff ladders, prompts (verbatim), SQL semantics, ordering. When the code and `PLAN.md` disagree, the code wins (`PLAN.md` describes the MVP and is stale). Do not redesign and do not fix bugs you find: record them in Known gaps and port them as they are, unless the bug is a security hole, in which case stop and write it in the Status table for the owner.
2. Port the tests too. Every `*.test.ts` in the area you port gets a Go test covering the same cases. Keep explicit clocks (`now` as a parameter) the way the TS code does.
3. Do not delete or edit TypeScript backend code before M10b. Until then both stacks live side by side and the TS tests keep passing.
4. No commits, no stash, no push, no PRs, no posting anywhere (GitHub, Linear, Slack, email). A push to `main` deploys to production. Leave the work in the working tree. The owner commits and merges.
5. Production is read-only and mostly off limits. Never touch container `recall-app-1`, volume `recall_data`, compose project `recall`, port 4800, the deploy checkout `~/selfhost/recall`, or the main checkout `~/Code/JS/Node/2026/recall` (reading the model files from it is the one exception, see Embeddings). Never copy the production database, a production backup, or the production `.env`. Never call the live gateway (`http://127.0.0.1:8793`), Resend, Google, or the Hugging Face Hub from tests.
6. Scratch runs use compose project `recall-go-dev`, image tag `recall-go:dev`, and a port from 4870 to 4879 (check it is free with `lsof -nP -iTCP:<port> -sTCP:LISTEN` first; 4800 to 4806 and 4893 are taken). Scratch servers get a fake gateway, no Resend key, no Google credentials, and a database seeded by the TS code. Remove every scratch container, volume and image you made before the milestone ends. Never run `docker system prune`, `docker builder prune` or `docker volume prune`: other projects share this Docker.
7. One heavy process at a time (install, build, test run, typecheck, docker build), never in parallel, including across subagents. Before each one run `df -h /System/Volumes/Data | tail -1`, `memory_pressure | tail -1` and `sysctl vm.swapusage`. Free disk was 13 GB at the start and the machine alerts under 10 GB: if a step would leave less than 10 GB free, first remove your own caches (`go clean -cache`, scratch images, your own build output), and if that is not enough, stop and report the numbers in the Status table. Never start a dev server in the background. Follow the global instructions on dev servers and the heavy lock.
8. Never type a tool or dependency version from memory. Use `go version` for the `go` directive, `go get <module>@latest` for dependencies, `docker manifest inspect <tag>` before using an image tag, and read versions of the TS side from `apps/app/package.json` and `pnpm-lock.yaml`. Repo pnpm is 10.17.0: use `npx -y pnpm@10.17.0 ...` or `bash scripts/setup-worktree.sh`, never bare `pnpm`.
9. The Bash hook blocks commands that contain the text `.env` or read environment variables. Write such files with the Write or Edit tool.
10. English only in code, comments, docs and test names. No em dashes anywhere. Follow `AGENTS.md` (Migrations, Production) and the global instructions.
11. Finish a milestone only when its gate passes. Never mark one done with failing or skipped tests. A test that needs the model or the ONNX library must run, not skip. If something cannot be finished, say exactly what and why in the Status table and stop there.
12. Every claim in the Status table is something you ran and saw. Record the command and the numbers (test counts, bytes, MiB).
13. After each milestone's gate passes, save a snapshot outside the worktree so a lost worktree does not lose the work: `git diff --binary HEAD > ~/.cache/recall-go-port/M<n>.patch` and a tar of the untracked source files (no binaries, no downloaded libraries, no `node_modules`) next to it. Create the directory first. This is not a commit and not a stash.

## Gates

Every milestone, from `apps/server`:

```bash
gofmt -l .            # prints nothing
go build -tags sqlite_fts5 ./...
go vet -tags sqlite_fts5 ./...
go test -tags sqlite_fts5 ./...
```

Every `go` command takes `-tags sqlite_fts5` (Decisions log, M0): `github.com/mattn/go-sqlite3` compiles FTS5 in only under that tag. Without it `db.OpenRaw` refuses to open, so a missing tag fails loudly. The tests also need the ONNX Runtime library (`scripts/fetch-onnxruntime.sh`, once per machine) and the model files in `apps/app/data/models`.

Use `go test -race` on packages with goroutines (jobs, embed, httpapi, auth rate limits).

The TS side must still pass until M10b, from `apps/app` (only rerun when you touched TS or shared files):

```bash
npx tsc --noEmit
npx vitest run
```

And from the repo root: `node --test integrations/claude-code/test/*.test.mjs`.

From M8 on, the dashboard gates (typecheck, tests, build) run on the SPA. M10 adds the image build, the size and memory measurements, and the container smoke test.

## Target architecture

```
apps/server/                 Go module (go.mod here)
  cmd/recall/                one binary: `recall serve`, the admin commands, `recall healthcheck`, `recall embed-child`
  internal/config            environment config (same variables and defaults as src/server/config.ts)
  internal/db                open, pragmas, sqlite-vec, embedded migrations, schema state
  internal/embed             tokenizer, ONNX session, the child process and its idle stop
  internal/<domain>          one package per area of src/server (search, pipeline, jobs, people, reminders, ...)
  internal/auth              sessions, passwords, passkeys, workspaces, the OAuth server
  internal/httpapi           HTTP server: /health, /v1, /mcp, /api/auth, well-known, RPC, static dashboard
  internal/web               embedded dashboard build (copied in at build time)
  testdata/                  golden files exported from the TS code
  testdata/gen/              the TS scripts that export them
apps/app/                    dashboard: Vite + TanStack Router SPA, no server code (after M8)
apps/site, apps/edge, integrations/claude-code   unchanged, stay as they are
```

Decisions already made. Change one only with a written reason in the Decisions log.

- **One process, one binary.** `recall serve` runs the HTTP server and the job loop. The embedding model runs in a child process that is the same binary (`recall embed-child`), started on first use and stopped after `RECALL_EMBED_IDLE_MS` (default 600000) without a request, exactly like `embed.ts`: one inference at a time, batches of 4, requests fail when the child dies, and the parent exiting stops the child. `RECALL_EMBED=inline` keeps the in-process mode for tests and the CLI.
- **Same database file, same data.** The Go binary opens the existing `$DATA_DIR/recall.db` in place. No data migration, no new migration during the port. The old image must still be able to open the database after the Go binary has written to it, because that is the rollback.
- **cgo is allowed.** ONNX Runtime and sqlite-vec are C libraries, so this binary is not static like Palui's. SQLite: `github.com/mattn/go-sqlite3` with FTS5 compiled in, plus the sqlite-vec 0.1.9 C source vendored and registered as an auto extension. Pin sqlite-vec to exactly 0.1.9 (production reports `vec: "v0.1.9"`): the `vec0` shadow tables were written by it. The published Go bindings stop at v0.1.6, so do not use their bundled source. Plain `database/sql` with handwritten SQL, no ORM, always name columns. If M0 shows a pure-Go route that passes every M0 check (for example `github.com/ncruces/go-sqlite3` with a sqlite-vec 0.1.9 build), it may be chosen instead, with the measurements written down.
- **Write discipline.** The TS code relies on synchronous better-sqlite3 calls so claims never interleave. In Go use one write connection (a pool capped at one) plus a read pool, and keep every claim a single statement or one transaction on the write connection.
- **Embeddings: ONNX Runtime through cgo**, with the same model files the TS build uses. See Embeddings below. A Node sidecar is not acceptable (it would keep the 123 MB `node` binary in the image).
- **Final image.** Needs glibc and libstdc++ for the official ONNX Runtime build, no Node, user and group 1000:1000 (the volume's files are owned by uid 1000, the `node` user of the old image), `/data` as the volume, a healthcheck that is a `recall healthcheck` subcommand. `scripts/pre-deploy.sh` and `scripts/backup.sh` run shell snippets inside the container today (`sh -c`, `ls`, `sort`, `xargs`, `rm`): either keep a shell in the image or replace those with CLI subcommands. Choose the smallest base that passes the smoke test and record the layer sizes. Order of preference: a distroless glibc base, then `debian:bookworm-slim`.
- **HTTP: the standard library** (`net/http`). JSON responses must match the TS build byte for byte where no clock, random id or model output is involved (key order, `null` against `[]`, number formatting). Palui's `internal/jsonx` has JS-compatible number formatting.
- **MCP server.** Try the official Go SDK (`github.com/modelcontextprotocol/go-sdk`) as a stateless Streamable HTTP server with JSON responses. If it cannot reproduce the goldens (initialize result, `tools/list`, tool results, the 401 challenge, the answers to GET and DELETE), write the small JSON-RPC handler by hand: Recall only serves `initialize`, `ping`, `notifications/initialized`, `tools/list` and `tools/call`.
- **Auth: no Better Auth.** Go owns sessions, username and password sign-in, passkeys (`github.com/go-webauthn/webauthn`, see Palui's `internal/auth`, which was golden-checked against the same Better Auth 1.7.18), workspaces on the `organization` and `member` tables, and the OAuth 2.1 authorization server on the `oauth_*` tables. See Compatibility for what must keep working.
- **Dashboard API.** Each of the 48 server functions becomes `GET` or `POST /app/api/rpc/<functionName>` with the same input and output JSON. The path is under `/app` on purpose: the edge worker (`apps/edge/src/routing.ts`) already routes `/app/*` to this server, so no Cloudflare deploy is needed. On the dashboard side the files that export the functions keep their names and exports and become thin `fetch` wrappers, so call sites do not change. Every endpoint keeps its guard: session required where it is today, same-origin on every write.
- **Validation.** zod is 4.6.7 here and in Palui's port: copy Palui's `internal/zod` and keep zod's issue texts wherever an error body shows them.
- **LLM gateway client.** Raw HTTP to `${GATEWAY_URL}/v1/chat` with the same body, the same SSE parsing rules, the same JSON extraction, retry and model fallback as `src/server/gateway/client.ts`. Keep the model ids that are in `config.ts` as they are. Tests use the fixtures in `src/server/gateway/fixtures` and a fake gateway.
- **PDF text.** `unpdf` is pdf.js, which has no Go port. Pick the Go library whose output is closest on the test fixtures plus a few real PDFs, keep the page handling and the title rule, and record the differences in Known gaps. Stored documents are already text, so this only affects new uploads.
- **HTML to text.** Use the Readability port Palui chose (see its webfetch connector and Decisions log), checked against goldens from Mozilla Readability on linkedom.
- **Time.** The standard `time` package with `time/tzdata` embedded. Port `src/lib/dates.ts` and the reminder clock rules exactly (Palui's `internal/zone` may help).
- **JavaScript semantics.** Go's regexp is RE2: no lookbehind (`chunk.ts` uses one), `\s` and `\w` are ASCII-only while JavaScript's `\s` covers Unicode spaces, and case folding differs. Port each regular expression deliberately and golden-test it, above all in `chunk.ts`, `sensitive.ts`, `embed-model.ts` (the whitespace collapse before embedding), `usernames.ts` and the FTS query builder. Length limits in zod count UTF-16 code units. `toLowerCase`, `trim` and `localeCompare` are not Go's `ToLower`, `TrimSpace` and byte order.

## Compatibility contracts

Each of these has a golden test.

- **Migrations.** Tracking table `_migrations(name TEXT PRIMARY KEY, applied_at INTEGER)`, `applied_at` in Unix ms. Identity is the file name. Statements split on `--> statement-breakpoint`, one transaction per migration. Copy the 13 files from `apps/app/drizzle/*.sql` into the Go module with the same names and the same order as `scripts/bundle-migrations.ts` produces (there are two `0006_*` files and production has both applied). A test keeps the copies identical to the TS ones while those exist. Never rename or edit a shipped migration.
- **Schema state.** `/health` answers 200 `{"ok":true,"vec":"v0.1.9"}` and 503 `{"ok":false,"error":"db_newer_than_app"}` when the database has migrations this build does not know. Port `health.ts` exactly.
- **Pragmas on every connection:** `journal_mode = WAL`, `synchronous = NORMAL`, `foreign_keys = ON`, `busy_timeout = 5000`.
- **Timestamps.** Recall's tables store integer Unix ms. Better Auth's tables store `timestamp_ms` integers. Fact dates are `YYYY-MM-DD` text with a precision column. JSON columns are text. Check the stored form of every column against a TS-seeded database, never against `schema.ts` alone.
- **Search indexes.** `chunks_fts` and `memories_fts` are FTS5 with `porter unicode61 remove_diacritics 2`. `chunks_vec` and `memories_vec` are `vec0` with `embedding float[384] distance_metric=cosine` and partition keys `workspace_id` and `container`. Vectors are bound as 1536 bytes of little-endian float32. Only current memories are indexed. The triggers that refuse an empty `workspace_id` stay as the migrations made them.
- **Embeddings.** Model `Xenova/multilingual-e5-small`, the quantized ONNX file, 384 dimensions, text `"<kind>: " + collapsed text` with kind `query` or `passage`, truncation at 512 tokens, mean pooling over the attention mask, L2 normalization. Token ids must equal the TS build's exactly on the golden corpus. Vectors must have cosine similarity of at least 0.9999 with the TS build's on the same platform. Dedupe fires at 0.975 and people matching uses its own thresholds, so drift changes behavior.
- **Model files.** Read and write the same layout the TS build cached, so production needs no new download: `$MODELS_DIR/Xenova/multilingual-e5-small/{onnx/model_quantized.onnx,tokenizer.json,config.json,tokenizer_config.json}`. SHA-256 of the files production runs today:
  - `onnx/model_quantized.onnx` (118308185 bytes): `f80102d3f2a1229f387d3c81909990d8945513e347b0eab049f7de3c6f98c193`
  - `tokenizer.json` (17082730 bytes): `0b44a9d7b51c3c62626640cda0e2c2f70fdacdc25bbbd68038369d14ebdf4c39`
  - `config.json`: `cb99455288675345e1a4f411438d5d0adbba5fbd3a67ea4fb03c015433b996c1`
  - `tokenizer_config.json`: `a1d6bc8734a6f635dc158508bef000f8e2e5a759c7d92f984b2c86e5ff53425b`
  When the files are missing, the server downloads the same files from the same Hub URLs the TS build uses, as it does today on first boot.
- **API keys.** `rcl_` plus 32 base62 characters, stored as the SHA-256 hex of the whole key, prefix the first 10 characters. Keep the generation rule as it is (including its modulo bias). `last_used_at` writes stay throttled.
- **OAuth tokens.** Access `rco_`, refresh `rcr_`, stored as SHA-256 base64url without padding of the part after the prefix. Tokens, clients, consents and refresh tokens that Better Auth wrote must keep working: a claude.ai connector that is connected today must still work after cutover without reconnecting, including its next refresh. The OAuth endpoint paths under `/api/auth/oauth2/*` and both well-known documents keep their paths and their JSON, because clients have cached them.
- **Passwords.** Read `src/server/auth.ts`: the scrypt form that is current and the legacy `pbkdf2$sha256$100000$...` form. Hashes made by the TS build must verify in Go, and hashes made by Go must verify in the TS build (rollback).
- **Passkeys.** Existing rows keep working (same row encoding as Better Auth 1.7.18 on `@simplewebauthn/server`). Palui's passkey golden shows how to prove it.
- **Connector secrets.** AES-256-GCM, key HKDF-SHA256 of `CONNECTOR_SECRET` (salt `recall-connectors`, info `connector-tokens-v1`), 12-byte IV, the row context as AAD, text form `v1.<iv>.<ct>.<tag>` in base64url. Note the order is ciphertext then tag, unlike Palui.
- **Ids.** `<prefix>_` plus 16 characters from `0123456789abcdefghjkmnpqrstvwxyz`, 16 random bytes masked with 31. Keep every prefix. Check which id form Better Auth's tables use in a seeded database and keep producing rows the TS build accepts.
- **REST.** Every route in `src/routes` outside the dashboard: method, path, status, headers that clients read, body. Auth by `Authorization: Bearer rcl_...` or `X-API-Key`. OAuth tokens do not reach `/v1`.
- **MCP.** Server name `recall`, version `1.0.0`, the `instructions` string, the eight tools with their names, descriptions and input schemas, the result texts, the error mapping, the per-caller limit on `ask_memory`, and the 401 with `WWW-Authenticate`.
- **Clients that exist today** and must keep working without a change: Palui's Recall connector (`~/selfhost/palui/apps/server/internal/connectors/recall`, read it: every field it reads must be covered by a golden), the Claude Code hooks in `integrations/claude-code` (`GET /v1/profile`, `POST /v1/memories`), the `mcp-recall` skill through mcporter, and claude.ai connectors through OAuth.
- **Jobs.** Rows in `jobs` that the TS build queued (all 8 types, their payload JSON) must run in Go, and the reverse. Keep the claim order, the backoff ladder `[30s, 120s, 600s]`, `MAX_ATTEMPTS = 4`, the crash recovery rules, the 7-day pruning, and the hourly `reminders` and `app_sync` rescheduling.
- **Email.** The Resend request and its `Idempotency-Key` keep their form, so a reminder sent by the TS build is not sent again by Go.
- **Backups.** `recall backup <dest>` writes the same thing the TS CLI does (a consistent snapshot, gzipped), so `scripts/backup.sh`, `scripts/pre-deploy.sh` and a restore keep working.

Allowed to change at cutover: dashboard session cookies (people sign in again), the in-memory rate-limit counters, in-flight `ask` and `wait=true` requests (they fail as on any restart), and the server-function wire between the dashboard and the server (they ship together).

## Embeddings

This is the part with no precedent in the Palui port, so M0 proves it before anything else is built.

- Read `embed-model.ts`, `embed.ts`, `embed-child.ts` and `tokenizer-compact.ts`, and the versions in the lockfile (`@huggingface/transformers` 4.3.2, `onnxruntime-node` 1.30.0 at the time of writing: confirm).
- Tokenizer: the model's `tokenizer.json` is an XLM-R Unigram tokenizer with a 250k vocabulary. The spec is what transformers.js produces, which may differ from the Rust `tokenizers` library in corner cases. Candidates: `github.com/daulet/tokenizers` (the Rust library through cgo), the tokenizer inside `github.com/knights-analytics/hugot`, `github.com/sugarme/tokenizer`, or a hand-written Unigram. Choose by the golden corpus: the ids must be equal for every text.
- Inference: `github.com/yalue/onnxruntime_go` (or hugot's ORT backend) with the official ONNX Runtime shared library. Prefer the ONNX Runtime version the TS build runs if the binding supports it. Session options as in the TS build: CPU memory arena off, memory pattern off. Feed `input_ids`, `attention_mask` and whatever else the model's inputs list, padded to the longest text in the batch.
- The shared library is needed in three places: macOS arm64 (local tests), Linux x64 (CI) and Linux arm64 (the image). Fetch it with a script that pins the version and checks a SHA-256. Do not commit binaries.
- Model files for local tests: copy them from `~/Code/JS/Node/2026/recall/apps/app/data/models` into `apps/app/data/models` in this worktree (a read of that checkout, nothing else there may be touched), and check the four SHA-256 values above. If they are missing or differ, stop and report.
- Golden corpus (exported by the TS build, at least 200 texts): English, Indonesian (formal and casual), mixed-language, CJK, Arabic, emoji and ZWJ sequences, combining marks, texts with tabs, newlines, non-breaking and other Unicode spaces, the empty string after trimming, one character, texts well past 512 tokens, text with secrets masked, both kinds. For each: the exact string fed to the tokenizer, the token ids, and the vector.

## Milestones

Run in this order. Each lists the TS sources to port. Read the sources, do not rely on this list being complete: if `src/server` has a file that no milestone names, add it to the right milestone here.

**M0 Spike and decision.** Set up the worktree (`bash scripts/setup-worktree.sh`, after the disk check). Create the Go module and the golden generator. Prove four things on macOS arm64: (1) tokenizer ids equal the TS build's on the corpus, (2) vectors reach cosine 0.9999 or better, (3) the Go binary opens the TS-seeded database with sqlite-vec 0.1.9 and FTS5, and a KNN query and an FTS query return the same rows in the same order as the TS build, then the TS build opens the same file again after Go wrote a row to each indexed table, (4) measured memory of the embedding child (RSS after load, after one batch of 4 long texts, after 20 batches) next to the same numbers for the TS child run locally, and the binary size. Then one image build on Linux arm64 to record the real image size and to prove the libraries load there. Gate: all four hold. Stop and report to the owner, without going further, if (1) or (2) cannot be met, if (3) fails, or if the Go child holds more memory than the TS child.

## Known gaps

Add anything ported with a behavior difference, any TS bug ported as it is, and anything left for the owner, with the file it lives in.

- M0 `internal/embed/nfkc.json`: NFKC follows the Unicode version of the Node that exported the table (17.0, Node 24.16). If the TS image's Node moves to a newer Unicode before cutover, regenerate it.
- M0 `internal/db`: go-sqlite3 compiles SQLite without `SQLITE_DQS=0`, `SQLITE_ENABLE_MATH_FUNCTIONS` and `SQLITE_ENABLE_STAT4`, which better-sqlite3 13.0.3 sets. The TS code uses no math functions and no `ANALYZE`; the only effect is that Go accepts double-quoted string literals that TS would reject, so ported SQL must keep single quotes for strings.
- M0 `internal/embed`: JavaScript strings can hold lone surrogates (`"\ud800"` in a JSON body); Go's JSON decoding turns them into U+FFFD, which the tokenizer then treats as a space. TS keeps the lone surrogate. Only reachable with deliberately broken input.
- M1 `internal/connectors/crypto.go` (for the owner, security): the TS `unseal` passes no `authTagLength`, so Node accepts a GCM tag cut to 4, 8 or 12 to 15 bytes (with a DEP0182 warning), which makes a forged sealed value (the Google OAuth state cookie, stored tokens) a 2^32 guess instead of 2^128. Go accepts only the full 16-byte tag. Values the TS build sealed always have 16-byte tags, so nothing stored stops opening. Not exploitable in practice (online guessing, the value is also bound to its context), so this was not treated as a stop condition; worth setting `authTagLength: 16` if the TS code lives on.
- M1 `internal/auth/passwords.go`: a stored pbkdf2 hash with more than 2^31-1 iterations makes the TS `verifyPassword` throw (a 500 at sign-in); Go answers false. Only a hand-corrupted hash has that.
- M1 `internal/config/config.go`: a `RECALL_URL` that `new URL()` refuses makes every TS `config()` call throw; Go gives an empty `passkeyRpId` and carries on.
- M1 `internal/mem`: the memory log line is `rss= heapInuse= heapSys= MB` (Go's heap) instead of V8's `heapUsed heapTotal external arrayBuffers`. On macOS `rss` is the peak. Logs only.
- M2 `internal/embed`: the TS `embed-child` loaded `config()` from its parent's environment through `fork`; the Go child gets the parent's environment plus `MODELS_DIR` the same way, but its log lines (`embedder ready (pid N), memory: ...`) go to stderr, not stdout, and the memory figures are Go's (see the M1 mem line).
- M2 `internal/embed/download.go`: transformers.js `fetch` uses undici's defaults (300 s headers and body timeouts, from the undici documentation, not measured here); Go uses the same numbers.
- M3 `internal/content/pdf.go`: PDF text comes from github.com/ledongthuc/pdf, not pdf.js. On the fixtures the words are the same and in the same order (the IRS W-4: 4762 words), and simple PDFs match exactly; line breaks and the spaces inside lines can differ on other documents. Only new uploads are affected.
- M3 `internal/gateway/stream.go`: when the gateway sends a malformed chunk, the error text after "bad stream chunk: " is not the AI SDK's exact validation message. Tool chunks (the gateway sends none) are validated but not tracked, so a tool chunk that refers to a missing tool call is not an error here.
- M3 `internal/gateway/schemas.go`: a reply that fails the schema twice stores `InvalidJsonError: invalid shape: [...]` (zod 4's message, the issue list as JSON); the issue texts are hand-written zod semantics and can differ from zod's in cases the goldens don't cover (the stored job error only).
- M3 `internal/content/fetch.go`: URL fetches send Go's `accept-encoding: gzip` (Go decodes it) where undici sends its own list (it can also take br and zstd). A server that only compresses with brotli answers uncompressed to Go. Only new URL documents are affected.
- M3 `internal/content/content.go`: the linkedom body rule follows htmlparser2's tree only as far as the document element's first two children; markup that relies on htmlparser2 quirks inside those (for example raw-text handling of `<iframe>` content in x/net's tokenizer, which htmlparser2 parses as markup) can still differ. 18 shapes are golden-tested.
- M3 `internal/pipeline/pipeline.go`: a file document whose `metadata.filename` or `metadata.mime` is not a string (only possible through hand-made metadata) uses the title or no mime in Go; TS would throw a TypeError on it.
- M3 `internal/jobs/runner.go`: when the bookkeeping write after a failure itself fails (a database error), Go logs it and still wakes waiters; the TS runner let the exception escape.
- M0 (not a port difference, for the owner): the TS build's vectors on a Mac differ from the ones it makes in production on Linux arm64 (cosine as low as 0.988 on the corpus). Dev databases and production are not interchangeable at the vector level, with either build.
- M4 `internal/connectors/gmailmessage.go`: an HTML entity for a lone surrogate (`&#xD800;`) in a Gmail snippet becomes U+FFFD in Go; JS keeps the lone surrogate. Display only.
- M4 `internal/dates/jsparse.go`: `JSParse` is a port of V8's DateParser (the ES5 format, then the legacy parser); the 74 strings in `apps.json` match. Local time comes from Go's zone rules, V8's from ICU, so a local form that falls in a DST gap or overlap can resolve to a different instant (the containers run in UTC).
- M4 `strx.LocaleCompare` (Oslo digest order, the fake feed, the profile's dynamic facts): exact ICU root order for ASCII (checked on every character pair and 4289 strings); a string with any non-ASCII character falls back to UTF-16 code unit order.
- M4 `internal/cli`: an error other than a user error (a disk or database failure) prints its message and exits 1; the TS CLI rethrew it, so Node printed a stack trace and exited 1.
- M4 `internal/cli/password.go`: a port of Node 24's readline key handling (99 keystroke sequences in `password.json` match). Left out: Ctrl+Z, which suspends the TS process with SIGTSTP and does nothing in Go; history keys, which do nothing in both since the prompt has no history; and input that ends before Enter, where TS keeps waiting and Go fails (a terminal in raw mode doesn't end).
- M4 `internal/backup`: when the online backup itself fails, Go removes the temp file; TS left `<dest>.tmp-<pid>` behind in that case.
- M4 `internal/backup`: the gzip stream comes from Go's `compress/gzip`, not Node's zlib, so `bytes` in the CLI output differs for the same database. Both are valid gzip of the same snapshot.
- M4 `recall` with no arguments prints the binary's one-line usage to stderr and exits 2; `cli.mjs` with no arguments printed USAGE to stdout and exited 0. `recall --help` and `recall --json` still print USAGE and exit 0.
- M4 `internal/connectors/gmailmessage.go`: single-byte charsets decode through tables read from Node's TextDecoder (exact). The CJK multi-byte ones (gbk, gb18030, big5, euc-jp, iso-2022-jp, shift_jis, euc-kr) use golang.org/x/text, which follows the WHATWG tables where Node's ICU converters don't: invalid bytes, extension ranges (HKSCS, UHC, user-defined areas) and how many bytes an error consumes. Valid common text decodes the same. `charset_test.go` pins the 66 of 884 golden cases that differ.
- M4 `internal/connectors/google.go`: a 2xx Gmail reply that isn't JSON fails with a SyntaxError in both, but the message is Go's, not V8's; a reply whose fields have the wrong JSON types fails in Go and is carried on in TS. Gmail doesn't send either.
- M4: a zero `maxBatches` (`people.Backfill`), `maxPages` (`apps.PullChanges`) or timeout (`ask.Ask`) means the default in Go and zero in TS. Only tests pass these.
- M5 `internal/jsonx`: JSON nested deeper than 10 000 levels is invalid JSON in Go (400 `invalid_json` where TS validates it).
- M5 multipart: `metadata` that parses to something other than an object, without a `document_date`, is dropped; TS stored it as is.
- M5 MCP: a batch with a request and a `notifications/cancelled` for it gets an answer in Go; the TS SDK never answers it. Request schemas are checked for initialize and tools/call only (tools/list's cursor type is not).
- M5 serve: NITRO_UNIX_SOCKET and NITRO_SSL_CERT/KEY are not supported (production uses neither); Node's 5 s keep-alive and 300 s request timeouts are Go's defaults instead; a database error checking the /mcp caller answers `Internal Server Error` as text, whose exact TS body was not traced.
- M5 router: a path outside the API (unknown path, wrong method) answers Go's 404 or 405 text; TS fell through to the SSR router (M8 replaces that side). `//v1/...` redirects with 301 in Go, 308 in TS.
- M6 OAuth: `private_key_jwt` client assertions are refused (`invalid_client`); Better Auth verified them. A registration's `jwks` is only checked for shape. Recall registers none (claude.ai is a public client).
- M6 OAuth: DPoP proofs are not verified and tokens are never bound: `token_type` is always `Bearer`, and a `DPoP` header on an unbound request is ignored. Where Better Auth required a proof (a DPoP client, a code with `dpop_jkt`, a bound refresh token, a resource that requires it) Go answers 400 `invalid_dpop_proof`. Recall's `/mcp` never accepted DPoP-bound use, so no working client depends on it.
- M6 routing: `/api/auth/...` paths are matched without case, percent-decoded, with trailing slashes trimmed and with an `/app` prefix (the M5 router rule); Better Auth answered 404 for `/API/Auth/...`, `.../token/`, `.../%74oken` and `/app/api/auth/...`.
- M6 OAuth: not ported (404 with an empty body): `/oauth2/end-session[/confirm]`, `create-client`, `get-client(s)`, `update-client`, `client/rotate-secret`, `delete-client`, `public-client`, `public-client-prelogin`, `client/rotate-keys`, `get-consent(s)`, `update-consent`, `delete-consent`. Neither the dashboard nor MCP clients call them.
- M6 OAuth: `BETTER_AUTH_SECRETS` (versioned secret envelopes) is not read; the secret is SESSION_SECRET, or a per-process random one when it is shorter than 32 characters, as in the TS build.
- M6 redirect URIs with a non-http(s) scheme are split by a small parser, not the full WHATWG parser for non-special URLs; exotic forms (percent-encoding, IPv6 hosts in custom schemes) may compare differently.
- M6 zod: registration and authorize validation report zod's first issue from hand-written checks; union and abort subtleties beyond the golden's cases may pick a different first issue.
